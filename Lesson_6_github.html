第3页·导入：从口头约定到机器可验证
约 5 分钟

验收为什么会扯皮？

现场：双方各执一词

  • 开发："功能我已经做好了，能跑。"
  • 用户："这根本没法用，太慢了。"
  • 开发："你说的'慢'是多少？"
  • 用户："就是……反正我不满意。"

问题出在哪

  • 第5课我们把"排队快一点"改成了≤3分钟的可验证标准
  • 但"做到什么算达标"还需要能被机器自动跑出来
  • 这就是今天要学的——测试用例：把 口头约定 变成 可自动核对的规则

提问：如果当初把"能用"写成什么具体内容，今天就不用吵了？

什么是"闭环"？做完 → 测 → 记录 → 改 → 再测，测试结果反馈回来驱动下一轮改进，形成一个不断循环的回路，而不是做完就交差。闭环思维本身就是一项重要的工程素养。

质量闭环：需求 → 用例 → 断言 → 运行 → 缺陷记录 → 迭代追溯

第6页·概念③：三类场景
约 8 分钟

两类方法 → 三类用例场景

场景用什么方法怎么设计用例食堂排队例子
正常场景有效等价类划分从合法输入里挑 1 个代表值，完整走通一遍流程12:10 排队实测 2.5 分钟→通过
异常场景无效等价类划分从不合法输入里挑代表值，看系统怎么处理客流激增实测 5 分钟、档口临时关闭、断网刷卡
边界场景边界值分析在阈值边界附近取 min / min-1 / max / max+1 / 空值3.0 临界达标、3.1 刚好超出、0 没人排队

一句话记住映射：正常＋异常＝等价类划分（各挑一个代表值），边界＝边界值分析（在阈值旁额外补几刀）。

为什么"0 没人排队"算边界而不是异常？因为它是输入的有效下限——排队人数可以合法地取到 0，只是正好压在边界上；而"断网刷卡""档口关闭"属于流程被破坏，才是异常。

第7页·概念④：断言与缺陷记录
约 8 分钟

断言三件套 + 缺陷记录五要素

assert 断言三件套

  • 主体：谁的什么指标
  • 阈值：多少算达标
  • 可复现路径：用什么输入能重现
# 食堂排队：把"要快"写成可验证的断言 # 主体=平均等待时间 阈值=≤3.0分钟 路径=午高峰实测 assert avg_wait_min <= 3.0, \ f"期望≤3.0分钟，实际{avg_wait_min}分钟"

缺陷记录五要素（写什么）

  • 复现步骤：一步步怎么操作能重现
    例：周一12:15到三号档口排队
  • 期望结果：按需求本应怎样
    例：≤3.0分钟取餐
  • 实际结果：实际发生了什么
    例：等了5.2分钟
  • 运行环境：在哪测的
    例：三楼食堂、周三午高峰、8档口全开
  • 严重级别：多严重
    例：中（体验差但未瘫痪）

测试失败 ≠ 写错代码——失败记录是需求澄清与质量改进的起点，缺五要素任何一项都是不合格的失败记录。

第8页·例题带教①：用AI生成hello函数和测试
约 8 分钟

例题：给 hello world 写单测

需求：每个程序员写的第一个函数 hello(name)——传名字返回问候语，不传参默认问候"世界"。不手写代码，全程让AI生成，重点学怎么提提示词。

提示词①（生成代码）：请用Python写一个函数hello(name)，传入名字返回问候语，不传参数时默认问候世界。
提示词②（生成测试）：请为上面的hello函数写pytest单元测试文件test_hello.py，覆盖正常、边界、异常三类场景，全部用assert断言。
# AI 生成的测试大概长这样（test_hello.py） def test_normal_default(): assert hello() == "你好，世界！" def test_normal_name(): assert hello("小明") == "你好，小明！" def test_boundary_empty(): assert hello("") == "你好，！" def test_boundary_long(): assert len(hello("a"*50)) > 0 def test_error_type(): with pytest.raises(TypeError): hello(123)
第9页·例题带教②：PyCharm现场跑
约 10 分钟

先看绿条，再看红条，关键是判断谁错了

1
绿条全过
PyCharm 右键 pytest 运行，5 条测试全绿——AI 生成的代码和测试对得上
2
故意改错期望
把空名字那条期望改成 "你好！"（函数实际返回 "你好，！"），跑出红条
3
关键判断
这条失败是代码错了还是测试期望写错了？函数符合需求设计——是测试期望写错，不是代码缺陷

记住：看到红条不要立刻改代码！先核对——是代码没按需求实现，还是测试期望本身写错了？这正是"测试失败≠写错代码"。AI 生成的测试会写对也会写错，要逐条用三要素和三类场景核对，不能照搬照抄。

回到食堂排队：正常（实测2.5分钟→过）｜边界（正好3.0分钟→过）｜异常（客流激增实测5分钟→记缺陷）。

第10页·随堂作业：用例编写工作坊
约 27 分钟

随堂作业：测试用例编写工作坊

1
选一条验收标准
基于本组第5次课《需求转化任务单》，选1条核心标准
2
写用例集
正常≥2条、边界≥2条、异常≥2条，每条写全三要素（前置条件、输入/操作、期望输出）
3
补1条断言
对其中1条口头约定补写assert：主体＋阈值＋可复现路径
4
填1张缺陷卡
把1条失败（或预判失败）用例填进缺陷记录卡（五要素）

写完后逐条自查：①期望输出写了具体值而非"成功""正常"；②边界取到min/min-1/max/max+1/空值；③异常覆盖空值与非法输入；④断言补全三件套；⑤缺陷卡五要素齐全。

第11页·小结与随堂检测
约 9 分钟

小结 + 随堂检测：5题快问快答

可测量、可复现、可追溯；测试失败 ≠ 写错代码

1. "用户名6—12位"按边界值分析要取哪几个值？
答案：6、5、12、13，外加空值（min、min-1、max、max+1、空值）
2. 哪个属于无效等价类？A 正常用户名　B 空用户名　C 正好6位　D 正好12位
答案：B（空用户名）——有效等价类是合法输入，无效等价类是不合法输入
3. "密码至少8位含数字"，正常场景和边界分别用什么方法？
答案：正常=等价类划分取合法代表值（8位含数字）；边界=边界值分析取7/8/9位
4. 失败记录只写"登录失败"，缺了缺陷五要素哪几项？
答案：复现步骤、期望结果、实际结果、运行环境、严重级别——五项全缺
5. 跑出来一条红条，第一反应该做什么？
答案：先核对是代码错了还是测试期望写错了，不要立刻改代码

思考题：全部测试通过能否说明功能一定满足用户需求？用例是不是写得越多越好？预习：版本控制与团队协作——如何让"需求—用例—缺陷"闭环可追溯。
